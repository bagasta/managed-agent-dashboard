# vuln-0004 — Unauthenticated payment webhook forgery renews paid subscriptions without payment (no Midtrans signature verification)

**Severity:** HIGH (CVSS 7.5)  
**Target:** https://chiefaiofficer.id  
**Endpoint:** `/payment-webhook`  
**Method:** POST  
**CWE:** CWE-345  
**CVSS Vector:** `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N`  
**Confidence:** high  
**Fix Effort:** medium  
**Finding Class:** dynamic  
**Filed by:** Payment Integrity Agent @ 2026-10-28 02:10:12 UTC

## Deskripsi

`POST /payment-webhook` on `https://chiefaiofficer.id` is an unauthenticated pass-through to an n8n payment workflow (`n8n.srv651498.hstgr.cloud/webhook/midtrans-aistaff`). It accepts arbitrary attacker-crafted payment events with no authentication and no Midtrans `signature_key` validation. A forged notification was demonstrated to renew a real paid customer's subscription (quota reset, 30-day extension) without any payment.

## Dampak

Any anonymous internet attacker can grant or renew paid subscription tiers for arbitrary customers at zero cost — direct revenue loss for the business and free access to paid AI-staff usage. Demonstrated: a real `tier_3 Business` customer's subscription had its usage quota reset (tokens_used 7,364,885 → 0) and expiry extended by 30 days (2026-11-12 → 2026-11-27) by a single forged request, with no payment involved. The same endpoint also processes `clevio_payment_create_checkout` events, letting an attacker spawn payment intents for any phone number.

## Analisis Teknis

The main SPA (bundle `/assets/index-BcT6OrpG.js`) builds a payment intent client-side and POSTs it to a webhook list: `["/payment-webhook", "https://n8n.srv651498.hstgr.cloud/webhook/midtrans-aistaff"]` with `Content-Type: text/plain`. `/payment-webhook` on the apex is a reverse-proxy pass-through to the n8n webhook (GET returns n8n's signature 404: "This webhook is not registered for GET requests"). The n8n workflow ("payment bridge") accepts two event shapes: (1) `clevio_payment_create_checkout` — client-defined fields incl. `phone_number`, `plan_code`, `display_amount`; (2) Midtrans-style notifications (`order_id`, `gross_amount`, `transaction_status`, `signature_key`). Neither path validates any credential: an empty JSON body, a forged Midtrans notification with a deliberately wrong `signature_key` (SHA-512 of a wrong key), and a forged checkout event all returned `200 {"message":"Workflow was started"}`. The workflow then applies subscription state changes server-side: ~20s after the forged checkout event (correlating `expires_at` = forged-event time + 30 days, proving causality), the target user's subscription record showed `tokens_used` reset to 0 and `expires_at` extended by a full 30-day period. No Midtrans server key is needed because the `signature_key` field is ignored (or absent from the checkout path entirely). The n8n webhook is also directly internet-reachable at `n8n.srv651498.hstgr.cloud/webhook/midtrans-aistaff`, bypassing the apex proxy. Related cross-tenant surface: `POST /v1/subscriptions/{user_id}/activate`, `/topup`, `/upgrade` on the apex mount accept any leaked agent `X-API-Key` to mutate other users' subscription records (verified: `/activate` on another tenant's user_id reaches business logic — returned 409 "User sudah memiliki subscription" rather than 401/403).

## Proof of Concept — Langkah

1. Read the victim's current subscription state via `GET /v1/subscriptions/{uuid}` (any leaked agent key works on the apex mount): `tokens_used=7,364,885`, `expires_at=2026-11-12`. 2. POST a forged payment event to `https://chiefaiofficer.id/payment-webhook` (no auth headers, `signature_key` deliberately invalid): `{"event":"clevio_payment_create_checkout","source":"chiefaiofficer_payment_bridge","bridge_reference":"pay-test-forged-1","phone_number":"<victim phone>","plan_code":"tier_3","display_amount":999000,"currency":"IDR",...}` → `200 {"message":"Workflow was started"}`. 3. Wait ~20s, re-read the subscription: `tokens_used=0`, `expires_at=2026-11-27T02:09:20.898Z` — exactly forged-event timestamp + 30 days. 4. Control: the same forged Midtrans notification with a wrong `signature_key` is likewise accepted (200), proving no signature check on the notification path either; the n8n webhook host accepts the same forgery directly.

## Bukti

Proxy-captured exchanges (Caido): forged checkout POST `/payment-webhook` 200 `{"message":"Workflow was started"}` (req 486); baseline `GET /v1/subscriptions/663c8137-...` 200 `tokens_used:7364885, expires_at:2026-11-12T03:22:34Z` (req 483); post-forgery re-read 200 `tokens_used:0, tokens_remaining:100000000, expires_at:2026-11-27T02:09:20.898113Z` (req 893) — the new expiry equals the forged request's timestamp + exactly 30 days, tying the state change to the forged event. Forged Midtrans notification with invalid `signature_key` also 200 (req 430); direct n8n webhook forgery 200 (req 431); empty body POST 200 (req 407); GET `/payment-webhook` returns n8n's webhook 404 format (req 465), identifying the backend.

## Asumsi

Attacker needs no account, no credentials, and no knowledge of any secret — only a victim phone number (enumerable via `GET /v1/agents` or `/v1/users/login/phone` behavior) and their UUID (returned by the phone-only login endpoint). The n8n workflow applies subscription renewals asynchronously (~20s).

## Counterevidence

Looked for controls that would neutralize this: no authentication on `/payment-webhook` (empty-body POST 200), no `signature_key` validation (wrong-key SHA-512 signature accepted, checkout-event path has no signature field at all), no WAF detected on any vhost (wafw00f clean), no rate limiting observed, and the n8n webhook is directly internet-reachable so the apex proxy provides no isolation. The only partial control found: `POST /v1/subscriptions/{id}/activate` returns 409 when a subscription already exists — but the webhook path bypasses that gate entirely, and the demonstrated forgery succeeded against an *existing active* subscription. Impact is bounded to subscription/quota state (no payment credentials or card data observed at this endpoint).

## Kondisi Perubahan Severity

If the n8n workflow were shown to only create checkout URLs without ever applying subscription state (e.g. the quota reset came from another concurrent test), severity would drop — but the expires_at ≡ forged-timestamp + 30d correlation rules this out; conversely, confirmation that forged `topup`/`activate`/`upgrade` calls with leaked keys mint arbitrary quota for arbitrary tenants would broaden the impact beyond renewals.

## Rekomendasi Perbaikan

Remove the public pass-through: the apex `/payment-webhook` route and the direct n8n webhook must not accept unauthenticated traffic. Verify the Midtrans `signature_key` server-side on every notification: SHA-512 over `order_id + status_code + gross_amount + server_key` compared to the received `signature_key`, and reject mismatches before any workflow node mutates state. Do not trust client-supplied `notification_url` or client-computed amounts/plan codes — look up the order server-side from the provider's transaction record (via Midtrans status API) using only the `order_id`, and apply plan/amount from that record. Never route payment state changes through a client-controllable webhook list. Make the subscription-update node in the n8n workflow idempotent and require a verified provider payload; bind renewals to provider transaction IDs rather than the event timestamp. Restrict the n8n webhook host (`n8n.srv651498.hstgr.cloud`) to internal networks or shared-secret auth, and remove the n8n `development` environment flag. Separately, enforce object-level authorization on `/v1/subscriptions/{user_id}/activate|topup|upgrade` so a leaked agent key cannot mutate another tenant's subscription.
