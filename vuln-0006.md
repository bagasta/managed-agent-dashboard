# vuln-0006 — Production PostgreSQL database exposed to the public internet on port 5432 (194.238.23.242 / srv651498.hstgr.cloud)

**Severity:** INFO (CVSS 0.0)  
**Target:** 194.238.23.242 (srv651498.hstgr.cloud)  
**CWE:** CWE-668  
**CVSS Vector:** `AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:N`  
**Confidence:** high  
**Fix Effort:** low  
**Finding Class:** dynamic  
**Filed by:** Postgres Exposure Agent @ 2026-10-28 02:12:13 UTC

## Deskripsi

The PostgreSQL 16.x database serving the Clevio AI Staff platform is reachable from the public internet on TCP port 5432 at the shared infrastructure host 194.238.23.242 (srv651498.hstgr.cloud). The service completes a full TLS/SSL handshake with any unauthenticated client, exposing the database's attack surface to the entire internet instead of restricting it to the application backend.

## Dampak

Any internet host can initiate PostgreSQL protocol handshakes against the production database. While no default or weak credentials were found (password auth is enforced, cleartext fallback declined), the exposure converts every future database-layer weakness — a leaked or weak application password, a new PostgreSQL CVE, a mis-scoped pg_hba.conf entry, or a new superuser with a bad password — into a directly exploitable remote compromise of the entire platform's data (customer records, chat transcripts, WhatsApp session data, payment state). It also enables unauthenticated protocol-level resource abuse (connection floods, auth-bruteforce pressure) against the database.

## Analisis Teknis

TCP port 5432 on 194.238.23.242 — the same host that terminates the platform's production HTTPS traffic (Traefik on 80/443) and n8n — completes PostgreSQL SSL handshakes for any unauthenticated client (`pg_isready` succeeds; `sslmode=require` and `sslmode=disable` both reach the auth layer). The server presents a certificate with CN `srv651498.hstgr.cloud` (valid 2025-12-08 → 2035-12-06), consistent with the PostgreSQL 16.11–16.12 fingerprint recorded during reconnaissance. Authentication is required on every handshake attempt: `psql` returns "password authentication failed for user X" for both `postgres` and an arbitrary nonexistent user, so there is no user-enumeration oracle, and a bounded dictionary of default credentials (postgres/admin/root/n8n/clevio users × postgres/password/admin/123456/root and postgres/postgres123/Password123 variants) failed in full — password authentication is enforced and defaults are not in use. Cleartext (non-TLS) connections are also accepted, meaning the password exchange can be attempted without transport encryption. The port carries the same 10-year Hostinger-issued TLS certificate as the host itself and was confirmed live across repeated probes during this scan window.

## Proof of Concept — Langkah

1. From an external host, confirm the port answers: run `pg_isready -h 194.238.23.242 -p 5432` — it returns "accepting connections".
2. Attempt a TLS connection without credentials: `psql "host=194.238.23.242 port=5432 user=postgres dbname=postgres sslmode=require"` — the server completes the TLS handshake and replies "password authentication failed for user postgres", proving an unauthenticated internet client reaches the database authentication layer.
3. Verify the cleartext path is equally open: repeat with `sslmode=disable` — same auth-required reply, confirming the port is fully reachable without TLS filtering.
4. Confirm the endpoint is internet-wide, not local-only: the same IP 194.238.23.242 also serves the production HTTPS traffic (ports 80/443), and the TLS certificate CN matches `srv651498.hstgr.cloud` (validity 2025-12-08 → 2035-12-06), i.e. the database shares the public production host.

## Bukti

pg_isready output: `194.238.23.242:5432 - accepting connections`. TLS server cert: CN=srv651498.hstgr.cloud, validity 2025-12-08 to 2035-12-06. Failed auth message: `connection to server ... failed: password authentication failed for user "postgres"` — identical for real and nonexistent users (no user-enum oracle). Cleartext handshake completes identically, proving the port itself is unfiltered and world-reachable. All dictionary credentials (postgres/admin/root/n8n/clevio × 5 common passwords × db postgres/n8n/clevio) rejected.

## Asumsi

Assumes the PostgreSQL instance on 5432 belongs to the Clevio AI Staff production stack (same host as the Traefik-fronted application services and n8n). No valid credentials were obtained, so no data access was demonstrated — this finding covers the network exposure itself.

## Counterevidence

No working credential found in a bounded ~20-attempt default-password dictionary across postgres/admin/root/n8n/clevio users and common db names (postgres, n8n, clevio). The server enforces password authentication on every handshake (no trust/auth-failure entry in pg_hba, no cleartext fallback: cleartext probes return the same auth-required error). No data could be read without credentials, so this is an exposure/hardening finding, not a confirmed compromise.

**Confidence rationale:** Dynamic probing executed directly against the live endpoint: pg_isready, cleartext/TLS handshakes, and a bounded credential dictionary across 6 usernames. The live server confirmed auth enforcement on every attempt.

## Kondisi Perubahan Severity

Discovery of any valid credential (leak, brute-force success, or a future PostgreSQL authentication vulnerability) would raise this to Critical; confirmation that 5432 is firewalled to specific source IPs would reduce it to informational.

## Rekomendasi Perbaikan

Firewall or bind the PostgreSQL service so it is not reachable from the public internet: restrict port 5432 to the application containers/host only (ufw/iptables rule, Docker network isolation, or cloud-provider firewall allowing just the app subnet). On the database side, ensure `pg_hba.conf` contains no broad `0.0.0.0/0` entries with weak or `trust` authentication, set `listen_addresses` to the internal interface, and enforce `hostssl`-only with scram-sha-256 for the remaining internal entries. Monitor `postgres` auth failure logs for brute-force attempts against the now-exposed instance.
